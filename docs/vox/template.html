(all vibe-proved by AI)

vox is an experimental extension of the OxCaml compiler in which types carry refinements, as in the examples below. Refinements become proof obligations, discharged at compile time by Lean 4’s grind or manually proven lemmas (or checked at runtime with assume_); a failed obligation is a compile error with a counterexample. Verification is opt-in per function.

How it works

  • Refinements are Lean propositions; anything provable in Lean can be a refinement.
  • Refinements can mention the variables in scope, function arguments included (dependent types); a program variable in a refinement denotes its logical Lean counterpart.
  • Refinements generalize pre/postconditions: they attach to any type, and the typechecker propagates them through data structures and polymorphic functions.
  • OCaml functions can be used in specs: marking a function total_ reflects it into the logic, and refinements can then call it.
  • Specs go on module signatures: an .mli can state a model and prove its theorems; clients verify against the interface alone. It can instead hide the model and export axioms as obligations the implementation must prove — even the representation type can stay abstract.
  • Automation: grind handles the common case; missed goals are proved with tactics next to the code and registered with @[grind]; everything is kernel-checked.
  • Failures produce counterexamples: the goal, the hypotheses in scope, and a violating input, at the offending expression.
  • Unique mutation using the mode system: RustHorn-style mutable borrows (see the parallel in-place quicksort demo).
  • Specs work as tests: reflected predicates are executable OCaml, usable as runtime checks (assume_) and as oracles for property-based testing, fuzzing, and AI-driven bug finding.

Refinement types, by example

In the first example, the compiler verifies that appending two lists adds their lengths. The specification needs a length function it can mention, so the setup is a list type and the usual recursive definition of length:

@EX_LEN@

The total_ keyword reflects len into the logic: the compiler emits it as a Lean def, Lean checks that it terminates, and refinements can then call it (allowing arbitrary OCaml functions in specifications would be unsound: from a definition like let rec f x = f x + 1 the logic would conclude 0 = 1).

@EX_APPEND@

Apart from the annotation on its result type, append is ordinary OCaml, and the compiled code is the same as without the annotation. Between the braces stands a proposition of the logic, written in OCaml syntax: _ denotes the value the type is attached to, in this case append’s result, and a and b are the function’s parameters. Refinements are dependent: a type may mention the program variables in scope. What gives this meaning is the correspondence between the two worlds: in a refinement, a program variable stands for the logical counterpart of its run-time value (a mathematical integer for an int, a Lean inductive value for a variant such as ilist, an opaque atom for values of other types). A refinement can therefore state a relation between run-time values: here, that the length of the result is the sum of the lengths of the arguments.

Refinement types are often met as range restrictions such as int{ _ >= 0 }. With dependency, refinements generalize pre- and postconditions: a refinement on the result is a postcondition, which the body must establish; a refinement on a parameter is a precondition (nth, below).

@EX_NTH@

The bounds on i are the precondition at work: every caller must prove them, and the body may assume them. Within the body, branch conditions are also in scope, so the recursive call discharges its bounds from i <> 0 and the Cons match. The Nil arm is dead code given the bounds, and calling unreachable_ there proves it: unreachable_ is an ordinary library function of type unit{ false } -> 'a, so the argument () must be constructed at an uninhabited type, and the obligation is false under the arm’s hypotheses, where assert false would defer the claim to run time.

Proof obligations arise in one way only: by constructing a value of a refined type. The body of append constructs its result, a caller of nth constructs the argument i, and unreachable_ () constructs () at a type nothing satisfies. All are discharged at compile time by the automation.

Weakening nth’s bound to i <= len l makes the Nil arm reachable, and verification fails with a counterexample:

@HERO_FAIL@
@HERO_FAIL_OUT@

A failed obligation is reported like a type error, at the offending expression, with the goal, the hypotheses in scope, and a candidate counterexample, rewritten to source names. This is also the feedback an agent receives when it writes the code or the proof. When the automation misses a correct obligation, the agent proves the missing lemmas in Lean and registers them with grind, and the check goes through.

A refinement can also appear under a type constructor: int{ _ >= 0 } list states that every element is nonnegative. Because the fact is part of the type, the typechecker propagates it, and polymorphic functions preserve it by instantiation: List.rev at 'a = int{ _ >= 0 } returns nonnegative elements with nothing to prove (in effect, unary parametricity).

Specs as tests

Proof is not the only way to enforce a contract. assume_ e compiles the refinement into a runtime check: the value flows through when the predicate holds, and the program raises when it does not. This is useful at a trust boundary — validate an input where it enters, and the fact is then available to proofs, so the code behind the boundary compiles without further checks:

@ASSUME_INLINE@

A violated assumption raises, with the predicate and the location:

@ASSUME_FAIL_OUT@

The same mechanism turns a property that is stated but not proved into an executable oracle: reflected functions are ordinary OCaml, so the specification can simply run, and each call checks the property. Property-based testing, fuzzing, or AI-driven input search could generate inputs and use the contract as the oracle:

@ASSUME_LEMMA@

Specs on module signatures

An .mli can carry a logical model of its module — definitions, lemmas, proofs — in an embedded Lean block. The block is compiled from the interface alone into a Lean module beside the .cmi (VoxSig_<Unit>.olean), and clients import that: they verify against the interface without reading the implementation, and the interface’s own proofs are not re-checked per client. Editing a spec changes the .cmi checksum, which forces clients to re-verify.

The interface chooses what to reveal. Definitions and proved theorems are facts a client may use — the transparent style, where the model is public. An axiom is the reverse: a fact clients may use but the implementation must prove. The implementation’s compile ends with a seal that re-elaborates the interface and requires a proved theorem with the same name and statement for every axiom; a module that cannot prove its interface’s laws does not compile. Marking an abstract type [@@vox.sort opaque] extends this to the representation: the type gets its own sort in the logic, laws can quantify over it, and the implementation proves them about the concrete type, which takes over the same solver-side name.

The examples, each in the branch’s test suite:

  • A BST behind a transparent model — bst.mli states whole-tree membership, the ordering invariant, and a model-level insert; bst.ml is checked against it arm by arm, with no proof text and no trust keyword; a client proves against the exported theorems, and an alternative interface states everything add does in one quantified refinement. The classic wrong-side bug is rejected with a counterexample naming a missed element.
  • The Patricia trie from OxCaml’s optimizer (middle_end/flambda2/algorithms/patricia_tree.ml), little-endian, the bit twiddling kept: ptrie.mli models the bit operations arithmetically and proves the bit theory from first principles in core Lean, so nothing about bits is axiomatized; ptrie.ml’s whole trust surface is three one-line bridges (vox does not reflect the bitwise operators); descending without checking the prefix is a compile error with a witness. The packed variant is big-endian like the compiler, prefix and branching bit packed into one int per branch; the invariant is stated about the packed int itself.
  • Sealed: one law, two implementations — step.mli exports a single law as an axiom; step_incr and step_double each prove it, and the same client body verifies against either; an implementation that cannot prove the law is rejected at its seal.
  • Full abstraction — oset.mli hides model and representation both; the implementation is a binary search tree, but a client and its proofs see only four axioms; a fact the axioms do not imply is rejected.

Automation

grind covers the same ground as an SMT solver (congruence closure, E-matching, linear arithmetic), so the common case feels like SMT-backed refinement types. When automation fails, you can prove a Lean lemma with tactics and register it with grind, or use a lemma from a Lean library.

Fast-doubling Fibonacci

We define three versions of Fibonacci: by naive exponential recursion, linear loop, and fast-doubling O(log n) iterations, and prove them equivalent. SMT can’t do this on its own, so we help it out with some lemmas:

@FIB_IMPLS@
@FIB_LEMMAS@
@GEN_LEAN@

Regenerated and checked on every compile: a Lean module over the compiler-built VoxCore (the tuple products live there), the reflected fib with its synthesized termination_by, the embedded lemma block verbatim, and one theorem per obligation (fifteen for this file), each closed by grind.

Unique mutation

OxCaml’s @ unique mode lets us reason about mutation within the pure refinement system, and @ local lets us model mutable borrows and slices and verify them with RustHorn-style prophecies. Today the borrows are library-encoded; OxCaml language support for borrows would make this much more ergonomic.

In-place parallel quicksort

We sort a slice into an array, in parallel — the sequential qsort is the same body with the two recursive calls made directly instead of under fork_join2:

@HERO_QSORT@

This quicksort eliminates bounds checks: indexing is statically proved, so the compiled code reads and writes without them.

To sort an array, borrow it and sort the loan: the borrow hands the array back, and the prophecy carries the conclusion onto its contents:

@QSORT_ARRAY@

What refinement types buy us

Because a refinement is part of the type, the language’s polymorphism transports facts with no verifier support. The fork_join2 above is the untouched library function: its type is polymorphic, so instantiating 'a at a refined unit is all it took to carry each task’s conclusion across the domain join. The same instantiation gives a first form of shared mutation — a ref whose contents type is an invariant: reads return the fact, and writes must re-establish it (a write that cannot is refused with a counterexample, demo/lean_poly.ml). And lazy memoizes through internal mutation, yet a lazy of a refined type forces to the refined value:

@POLY@

Some more demos

Sixteen more cards: ADTs, records, tuples, quantifiers, loop invariants, cross-module specs, interior mutability, separation logic.

Interior mutability demo/lean_pcell.ml

Mutable cells behind a linear token discipline: reads and writes consume and return a unique token, so facts about a cell’s contents cannot survive a write. Duplicated, stale, forged, and cross-cell tokens are compile-time errors.

@PCELL@

A tree flipped in place demo/lean_flip.ml

A mutable tree with a pure ghost model: flip swaps child pointers in place, its dependent signature model _ = mirror (model h) makes each recursive call the induction hypothesis, and flipping twice is provably the identity.

@FLIP@

A separation logic demo/lean_sep.ml

One unique token owns the heap; its refinement carries a reified assertion, and the frame is an explicit parameter. Reads recover the ghost values, writes rewrite the points-to chunks, and two live references are distinct because Star means disjoint.

@SEP@

In-place list reversal demo/lean_seplist.ml

The textbook separation-logic proof: Lseg (l, vs) owns a null-terminated segment holding the model list, the reflected rev_append is the specification, and reverse rewires next pointers node by node, returning the same cells holding the reversed list.

@SEPLIST@

Algebraic data types demo/lean_adt.ml

Constructors of simple variants appear in predicates; a match refines its scrutinee; injectivity and distinctness come from the solver’s datatype theory. The Nil branch below is unreachable, and that is proved: its facts are contradictory, so the bare 0 discharges against r = 3.

@ADT@

Records and projections demo/lean_records.ml

Immutable records become Lean structures. Field projection appears in predicates; functional update preserves the untouched fields’ facts.

@RECORDS@

Native tuples demo/lean_tuples.ml

Unlabeled tuples are structural: one polymorphic product per arity, so construction and fst/snd appear in predicates with no wrapper type and the predicate language stays untyped. Matching (or a destructuring let) contributes per-component facts, and tuples of int/bool compare with = in the logic.

@TUPLES@

Contracts as loop invariants demo/lean_fib.ml

Parameter refinements are preconditions, so a recursive function’s parameters can carry its invariant — here (a, b) = (fib i, fib (i+1)). Call sites discharge it as ordinary obligations, including at the literal seeds in fib_loop n 0 0 1 and the compound arguments (i + 1), (a + b).

@CONTRACTS@

Specs across modules demo/lean_reflectclient.ml

A total_ function’s definition is exported in its unit’s .cmi. Clients apply it in predicates and prove against it; the .cmi checksum forces re-verification when the definition changes.

@CROSSMOD@

Lemmas next to the code [%%vox.lean]

Hand-written Lean — lemma statements and their proofs — embeds in the module it concerns, is checked on every compile, and is exported through the .cmi. A solver error inside a block is reported at the block’s own source location.

@EMBEDDED@

Quantifiers demo/lean_quant.ml

forall_/exists_ and implication in predicates; binders are untyped and Lean infers their sorts. Here max2 is not just an upper bound but provably the least one — each branch proves the quantified conclusion under its path fact.

@QUANT@

Binary search demo/lean_binsearch.ml

Immutable arrays are a built-in theory: Iarray.length a and a.(i) appear in predicates and are reflected in expressions. In-bounds access, the bracket invariant, and the flip-point characterization of the result are all proved.

@BINSEARCH@

Integer square root demo/lean_isqrt.ml

Integer square root against a reflected sq: the result is bracketed by squares of the same function the program runs. The midpoint is reflected division; one nonlinear lemma is proved in an embedded block. Nothing in the file is assumed, and returning the wrong endpoint is caught with a concrete counterexample (x = 0).

@ISQRT@

Mutable locals, loop invariants demo/lean_mutable.ml

Reads of a let mutable variable name its current SSA version; every write mints a fresh one. A [@vox.invariant] formula is handled classically — asserted at entry, assumed at the loop head, asserted again at the back-edge — and may mention a for-loop’s index; after the loop it holds at one past the end.

@MUTABLE@

Binary search, imperative demo/lean_imp_binsearch.ml

The bracket invariant from the recursive lower_bound, restated as a loop annotation: two unrefined mutable indices, plain reads and writes, and the flip-point postcondition follows from the invariant and the negated guard.

@IMP_BINSEARCH@

Reflected arithmetic Vox_reflect

+ - * / mod, comparisons, and && || not carry their logical meaning, recognized by primitive rather than by name (a shadowed (+) is not addition). Division is OCaml’s T-division, totalized soundly under partial correctness. A branch condition contributes itself as a fact: writing if n <= 0 is enough.
