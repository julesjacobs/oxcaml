vox is an experimental extension of the OxCaml compiler in which types carry logical predicates, as in the examples above. Refinements become proof obligations, discharged on every ocamlc invocation by Lean 4’s grind; a failed obligation is a compile error that reports the goal, the hypotheses in scope, and a candidate counterexample. Specifications are ordinary OCaml: a recursive function marked total_ becomes its own logical definition, so code is verified against itself rather than a hand-maintained model, and parameter refinements act as contracts discharged at each call site. Where automation falls short, lemmas are stated and proved in Lean next to the code and registered with the automation. Specs, lemmas, and reflected definitions travel in .cmi files, so verification is modular and adopted per function; unannotated code compiles as before and never invokes the prover. For imperative code, OxCaml’s uniqueness/linearity/locality modes supply the ownership discipline, which is enough to build separation-logic-style verification of mutation as a small trusted library, with no changes to the mode checker. Trust is graded and explicit throughout: proved, runtime-checked, or trusted and greppable.

Verified so far

  • In-place quicksort (the example above): sorted-and-perm, sequential and fork-join parallel.
  • The Patricia trie from OxCaml’s own optimizer: the bit theory proved from first principles; three trusted one-liners.
  • A BST behind a model interface: one-path search proved equal to whole-tree membership.
  • Mutation over ghost models: in-place list reversal, a tree flipped in place, interior mutability.
  • Fast-doubling Fibonacci verified against its own naive definition; binary search, integer square root.
  • A safe nth (the first example above), no option and no default: the Nil arm is proved unreachable by unreachable_.
  • A bounds-check-free kernel: the dot product at 1.36× the checked loop; the sum matching hand-written unsafe_get.

Design choices

  • The spec language is Lean; the spec is the program: predicates are propositions about the logical counterparts of program values, and total_ reflects a function into the logic (Lean checks its termination). Only reflected functions can be called in predicates, for soundness.
  • Why refinement types: a parameter refinement is a precondition and a result refinement a postcondition, but a refinement can also sit inside a type: int{ _ >= 0 } list puts the fact on the elements, where the typechecker carries it and any polymorphic function preserves it with nothing to prove.
  • Why Lean: the refinement theory is Lean’s logic, not a decidable fragment; anything provable in Lean can back a refinement. grind gives SMT-style automation in the common case, a failed goal escalates to a tactic proof next to the code (work LLMs are now good at) that registers back into the automation via @[grind], and everything, automation included, is kernel-checked.
  • Counterexamples on failure: goal, hypotheses, and a violating input, reported at the offending expression in about a second.
  • Vibe-proved, kernel-checked: most of the Lean on the branch was drafted by LLM agents against grind’s counterexample feedback; Lean re-checks every proof on every build, so proof provenance does not affect soundness.
  • Modes as the ownership substrate: unique tokens, RustHorn-style borrows with prophecies, and a separation logic, all as libraries over the mode checker.
  • Graded trust: proved / runtime-checked (assume_) / trusted (assume_unchecked_ and friends); the trust surface is small and greppable.
  • Properties are separate from checking mechanisms: the same contract can be proved, runtime-checked, or handed to property-based testing as an oracle.
  • Proofs erase: verified code can use unchecked primitives, deleting runtime checks the compiler has proofs for.
  • The usual verification vocabulary: ADTs, records, tuples and quantifiers in predicates; loop invariants; mutable locals (SSA); cross-module specs.

The model, in brief

A refinement is a predicate on a type: int{ _ >= 0 }, int{ not (_ = 0) }. A refinement on a parameter is a contract: the body assumes it, and each call site must discharge it. Here the branch condition is sufficient, and the check is fully automatic:

@SIXTY@

What sits inside the braces is not OCaml but a term of the logic. Each OxCaml value has a logical counterpart: for an int, the mathematical integer (no overflow); for a simple variant such as ilist, the corresponding Lean inductive value; for other types, an opaque atom that supports equality. A variable in a predicate means the logical value of that variable, and the refinement as a whole is a proposition about logical values. Functions enter the logic only by reflection: total_ emits the function as a Lean definition, and only reflected functions can be applied inside predicates. The restriction is soundness, not convenience: every Lean function is total, so a partial or diverging function has no logical counterpart to name (from f x = f x + 1 the logic would conclude 0 = 1). The same picture fixes the corner cases: reflected division is OCaml’s T-division totalized with x / 0 = 0 in the logic where the program raises, which is sound under partial correctness.

Refinements generalize pre- and postconditions: a parameter refinement is a precondition and a result refinement a postcondition, but a refinement can also sit under a type constructor. int{ _ >= 0 } list states a fact about every element. The fact lives in the type, so the typechecker propagates it, and any polymorphic function preserves it by instantiation: List.rev at 'a = int{ _ >= 0 } returns nonnegative elements with nothing to prove; in effect, unary parametricity for free. Spelled as a contract, the same fact is a quantified invariant carried alongside the list and re-established at every step.

Proof obligations arise in two places: applications to refined parameters, as above (no annotation at the call site), and explicit refine_ e claims such as a result refinement or a stored value. Both are proved by Lean 4’s grind, invoked by the compiler; an undischarged obligation is a compile error. Trust is graded: assume_ e is checked at runtime (the compiler inserts the test), and assume_unchecked_ e is trusted outright. That is the main escape hatch, though not the only one; ghost declarations and the mutation library’s mode casts are trusted too, and the full accounting is in the trust table below.

The predicate language does not stop at a decidable fragment: predicates and reflected definitions land in Lean, so anything provable in Lean can back a refinement. For automation, grind covers the same ground as an SMT solver (congruence closure, E-matching, linear arithmetic), so the common case feels like SMT-backed refinement types. The difference shows up when automation fails. An SMT solver that answers "unknown" leaves you stuck. Here, a missed goal can be closed by stating a lemma next to the code and proving it with tactics, which is work that language models are now good at; the lemma is then registered with the automation via @[grind] attributes and patterns, so the push-button case gets stronger over time for that codebase. Lean’s lemma libraries (mathlib) live in the same logic and are usable infrastructure rather than theory to re-encode for a solver. The developments on this page prove everything from core Lean; wiring library imports into the prelude mechanism is routine roadmap. Finally, grind produces proof terms that Lean’s kernel checks, so the automation itself is not trusted: a solver bug cannot verify a falsehood.

Marking a recursive function total_ translates its body into the logic: the compiler emits it as an ordinary Lean def, Lean independently checks termination, and the function’s name becomes usable inside refinements. The program is its own specification — there is no second, solver-side copy to drift:

@REFLECT@

Each recursive call re-instantiates the declared signature at its actual arguments, which is the induction hypothesis, so the textbook proof goes through with no proof text of its own.

What a failure looks like

A proof failure is an ordinary compile error at the offending expression. It states what was to be proved, what was known, and a concrete input that breaks it:

@WRONG_SRC@
@WRONG_OUT@

The output shows the goal, the hypotheses in scope, and the arithmetic model the solver ended on, rewritten to source names. On linear goals the model is a genuine refutation; nonlinear atoms print as separate entries, so a model that is only linear-consistent is identifiable as such. The same information, back in about a second, is what an agent gets as feedback when it is the one writing the code or the proof. The same shape catches the classic search-tree bug (wrong-side descent) and the classic Patricia-trie bug (skipping the prefix check) with witnesses; both are shown below on real structures.

Costs and trust

What a claim on this page is worth depends on what is proved, what is checked at runtime, and what is assumed:

ConstructStatusNotes

parameter contractsProved Discharged at every application, at the argument’s logical name.
total_ definitionsDefinitional The emitted Lean def is the OCaml body; Lean independently checks termination.

assume_unchecked_ e, axiom in blocksTrusted The primary trust surface. In the Patricia trie it is three bit-twiddling one-liners.

The audit grep is assume_unchecked_ + Obj.magic + [@@vox.sort] over the trusted libs.

What it costs. Verification runs inside ocamlc. A typical fully-verified module in the suite adds on the order of one second of Lean per compile on a dev box; heavier developments with inductive Lean proofs (the trie, quicksort) cost proportionally more, and failures with small counterexamples report in under a second. Obligations are re-proved from scratch on every build, so there is no stale-proof state to manage, and editing a spec changes the .cmi checksum, which forces clients to re-verify. The compiler footprint is about 4,900 lines in typing/, plus real changes to arrows and unification for dependent binders and an elaboration-time annotation hoist. The build gains a dependency on a pinned Lean toolchain. Verification is opt-in per module, and unannotated code never invokes the prover.

When a proof fails. If a refactor breaks an obligation, the build goes red at that function, localized like a type error. But closing a hard goal can require writing Lean, so a verified module carries a real maintenance cost that belongs with the team that owns it. Automated discharge is also not guaranteed: grind can fail on a goal that is in fact true (nonlinear arithmetic, quantifier instantiation, timeouts). The options in that case, in order: prove a lemma once in an embedded block, downgrade the fact to a runtime-checked assume_, or leave the function unannotated. Refined types are rigid by design, and the inference sharp edges are documented in DESIGN.md.

Known limits, by design. Partial correctness: a diverging call proves nothing (termination is checked only for total_ definitions, by Lean). Ideal integer arithmetic: overflow is outside the model. No concurrency reasoning yet beyond mode-checked disjointness (fork-join above); shared-state protocols need an invariant layer that does not exist. Client-written axioms in lemma blocks join the trust surface silently today; a lint is planned. All documented in DESIGN.md.

Properties versus checking mechanisms. A contract is written once, independent of how it is enforced. Today the mechanisms are proof (Lean) and runtime checking (assume_ e compiles the predicate into a test). Since reflected specifications are executable OCaml, the same contract can also serve as the oracle for property-based testing: quickcheck-style generators, fuzzers, or LLM-guided search for violating inputs, none of which exist yet in vox, all of which would consume the specs unchanged. Inductive invariants (a tree staying ordered under every insertion) are the facts sampling cannot confirm.

Hardening and proof provenance. Each feature on the branch shipped with an adversarial probe battery (forged tokens, duplicated loans, escaped borrows, prophecy reuse, cross-cell confusion, false exports), and every probe is pinned in the test suite to the layer that rejects it: modes, locality, contract, or Lean. A regression in any layer fails CI. The Lean itself, meaning the lemma libraries, the trie’s bit theory, and the invariant step lemmas, was mostly vibe-proved: drafted by agents against grind’s counterexample feedback and kept when the checker accepted it and the batteries held. Since Lean re-checks everything on every build, proof provenance does not matter for soundness, and agent-written proof text is safe to accept.

OxCaml’s modes

OxCaml’s mode system was built for allocation control, but it provides the ownership substrate a verifier needs to reason about mutation. A unique value has no other references, which is what justifies a strong update; the linearity axis (once) makes capability tokens affine; local confines a value to its region. vox added no checker machinery for any of the following. The mode checker enforces the ownership discipline, the refinements carry the ghost state, and a small trusted library (accounted for in the trust table above) encodes the heap logic on top; the mode checker’s existing reasoning is what keeps that encoding sound to thread. Rust’s verifiers (Creusot, Prusti, RustHorn) make an analogous move on the borrow checker. OCaml’s modes, designed for performance rather than verification, supply the same substrate, so refinement types reach in-place mutation through the mode system itself rather than through a bespoke ownership analysis.

Interior mutability demo/lean_pcell.ml

Mutable cells behind a linear token discipline: reads and writes consume and return a unique token, so facts about a cell’s contents cannot survive a write. Duplicated, stale, forged, and cross-cell tokens are compile-time errors.

@PCELL@

Mutable borrows demo/lean_borrow.ml

RustHorn-style: a borrow hands the continuation a loan whose final value is a prophecy variable p; the borrower proves an export in lender terms, and after resolution the lender reads the residual back with proof. Double use, forged exports, and writes through frozen loans are compile-time errors.

@BORROW@

A tree flipped in place demo/lean_flip.ml

A mutable tree with a pure ghost model: flip swaps child pointers in place, its dependent signature model _ = mirror (model h) makes each recursive call the induction hypothesis, and flipping twice is provably the identity.

@FLIP@

A separation logic demo/lean_sep.ml

One unique token owns the heap; its refinement carries a reified assertion, and the frame is an explicit parameter. Reads recover the ghost values, writes rewrite the points-to chunks, and two live references are distinct because Star means disjoint.

@SEP@

In-place list reversal demo/lean_seplist.ml

The textbook separation-logic proof: Lseg (l, vs) owns a null-terminated segment holding the model list, the reflected rev_append is the specification, and reverse rewires next pointers node by node, returning the same cells holding the reversed list.

@SEPLIST@

Quicksort, sequential and parallel demo/lean_qsort.ml

In-place quicksort over slice borrows, verified against sorted-and-perm: the recursion is a reborrow, and each side’s facts come home as prophecy values. Then the same verification runs fork-join: psort below carries the identical spec. The mode checker proves the two tasks own disjoint state, so parallelizing the recursion changes nothing in the proof; the trusted fork_join2 combinator (~20 lines) is where that guarantee is cashed out.

@QSORT@

Real code, verified as found

Two case studies on existing structures rather than examples written for the verifier. The first is the integer-set structure OxCaml’s optimizer uses (middle_end/flambda2/algorithms/patricia_tree.ml), as the classic little-endian toy: the GADT plumbing stripped, the bit twiddling kept, including i land b = 0, i land (b - 1), and the lowest-set-bit trick x land (-x) that appears verbatim in the compiler’s unpack. The interface models the bit operations arithmetically and proves the bit-level facts from first principles in core Lean, so nothing about bits is axiomatized. The trust surface is three one-line bridges (vox does not reflect the bitwise operators), each carrying its arithmetic model as its contract. From there the Patricia invariant, the one-path search, and insertion are proved arm by arm against the model.

@PTRIE_ML@

The whole trust surface of the module: three assume_unchecked_ one-liners bridging the bitwise primitives. Everything else is proved.

@PTRIE_MLI@

The interface carries the arithmetic bit theory and its lemmas: 346 lines of Lean written once, against an 89-line implementation containing no proof text — about four lines of theory per line of code for the hardest development in the prototype, exported through the .cmi so clients inherit it for free.

@PTRIE_CLIENT@

The model membership never reads a prefix, so clients reason about the trie with no bit operations at all.

The classic Patricia pitfall is descending by the branching bit without first checking the prefix, which files the key under a prefix it does not match (insert must join on a mismatch). It is a compile error with a witness:

@PTRIE_FAIL@
@PTRIE_FAIL_OUT@

And the FULL-fidelity variant (lib/ptrie_packed): big-endian like the compiler, with the prefix and the branching bit packed into one int per branch exactly as the compiler's prefix_and_bit packs them — pack is lor, and unpack recovers the bit with x land (-x). The invariant rides the packed int: for a well-formed node the bit IS its lowest set bit and the prefix IS the rest — theorems (lbit_pack), not fields. A hand-built node's packed int is therefore checked: mis-pack it and the invariant refuses with the decode in the counterexample.

@PTRIE_PACKED@

The model as the interface

bst.mli states the model (whole-tree membership, the ordering invariant, a model-level insert) and proves its theorems once, in the interface’s embedded block; definitions and theorems travel in the .cmi. The implementation is checked against them arm by arm: the efficient one-path search is proved equal to membership over the whole tree, and each insert arm is proved to build exactly the model’s tree. The implementation contains no proof text and no trust keyword, only refinement type annotations.

Three Fibonacci implementations: the naive recursion, reflected, is the specification; a tail-recursive accumulator loop carries its invariant in the parameter contracts; and O(log n) fast doubling is verified against the same fib. The doubling identities are proved in an embedded Lean block, by functional induction on the reflected definition itself — there is no second, solver-side Fibonacci. There is no trust keyword in the file: the halving step is reflected T-division (n / 2), and its parity annotation is proved.

The rest of the feature surface

Twelve more cards — ADTs, records, tuples, quantifiers, loop invariants, cross-module specs, reflected arithmetic. Expand if you want the breadth; nothing below is needed for the argument above.

Algebraic data types demo/lean_adt.ml

Constructors of simple variants appear in predicates; a match refines its scrutinee; injectivity and distinctness come from the solver’s datatype theory. The Nil branch below is unreachable, and that is proved: its facts are contradictory, so the bare 0 discharges against r = 3.

@ADT@

Records and projections demo/lean_records.ml

Immutable records become Lean structures. Field projection appears in predicates; functional update preserves the untouched fields’ facts.

@RECORDS@

Native tuples demo/lean_tuples.ml

Unlabeled tuples are structural: one polymorphic product per arity, so construction and fst/snd appear in predicates with no wrapper type and the predicate language stays untyped. Matching (or a destructuring let) contributes per-component facts, and tuples of int/bool compare with = in the logic.

@TUPLES@

Contracts as loop invariants demo/lean_fib.ml

Parameter refinements are preconditions, so a recursive function’s parameters can carry its invariant — here (a, b) = (fib i, fib (i+1)). Call sites discharge it as ordinary obligations, including at the literal seeds in fib_loop n 0 0 1 and the compound arguments (i + 1), (a + b).

@CONTRACTS@

Specs across modules demo/lean_reflectclient.ml

A total_ function’s definition is exported in its unit’s .cmi. Clients apply it in predicates and prove against it; the .cmi checksum forces re-verification when the definition changes.

@CROSSMOD@

Lemmas next to the code [%%vox.lean]

Hand-written Lean — lemma statements and their proofs — embeds in the module it concerns, is checked on every compile, and is exported through the .cmi. A solver error inside a block is reported at the block’s own source location.

@EMBEDDED@

Quantifiers demo/lean_quant.ml

forall_/exists_ and implication in predicates; binders are untyped and Lean infers their sorts. Here max2 is not just an upper bound but provably the least one — each branch proves the quantified conclusion under its path fact.

@QUANT@

Binary search demo/lean_binsearch.ml

Immutable arrays are a built-in theory: Iarray.length a and a.(i) appear in predicates and are reflected in expressions. In-bounds access, the bracket invariant, and the flip-point characterization of the result are all proved.

@BINSEARCH@

Correct, not just safe demo/lean_isqrt.ml

Integer square root against a reflected sq: the result is bracketed by squares of the same function the program runs. The midpoint is reflected division; one nonlinear lemma is proved in an embedded block. Nothing in the file is assumed, and returning the wrong endpoint is caught with a concrete counterexample (x = 0).

@ISQRT@

Mutable locals, loop invariants demo/lean_mutable.ml

Reads of a let mutable variable name its current SSA version; every write mints a fresh one. A [@vox.invariant] formula follows the classical quadruple — asserted at entry, assumed at the loop head, asserted again at the back-edge — and may mention a for-loop’s index; after the loop it stands at one past the end.

@MUTABLE@

The same search, imperatively demo/lean_imp_binsearch.ml

The recursive bracket invariant of lower_bound, worn as a loop annotation: two unrefined mutable indices, plain reads and writes, and the flip-point postcondition falls out of the invariant together with the negated guard.

@IMP_BINSEARCH@

Reflected arithmetic Vox_reflect

+ - * / mod, comparisons, and && || not carry their logical meaning, recognized by primitive rather than by name (a shadowed (+) is not addition). Division is OCaml’s T-division, totalized soundly under partial correctness. A branch condition contributes itself as a fact: writing if n <= 0 is enough.

Where this goes

Everything above exists and is CI-checked today, on unmodified OxCaml modes and a stock Lean. Directions this opens, roughly in order:

  • Verified kernels behind ordinary interfaces. Hot-path routines (parsers, codecs, index arithmetic, allocation-free data structures) proved once, exporting plain OCaml types to unannotated callers, with their defensive checks deleted (the benchmark above is the seed).
  • Specifications for the code we already trust most. Interface models for core containers and protocol layers, so client code can prove against them without reading implementations — the BST/trie shape, applied to the standard library.
  • Concurrency. Mode-checked disjointness already covers fork-join parallelism; an invariant layer for shared state is the natural next research step. Prototype token encodings to build on exist; choosing and hardening one is part of that work.
  • Spec-driven testing. The same contracts Lean proves are executable predicates, so every refinement is a ready-made oracle for property-based testing at the assume_ boundary, from quickcheck-style generators to search-based methods (including LLM-guided input search) hunting for violations of the facts not yet proved. One spec is enforced by proof where possible and by testing where not.
  • Hardening for untrusted code. Confining the trust surface (assume_unchecked_, block axioms) to designated modules, so a library’s verification claims are meaningful to downstream users by construction.

Verification here is not free, but the prototype gives a measurement of the current costs when the language itself is the proof surface: ordinary OCaml as the spec language, automatic discharge in the common case, four lines of once-written theory per line of the hardest code here, adoption one function at a time, and part of the cost returned as deleted runtime checks. The proofs that exist were mostly agent-drafted and machine-checked; the human effort went into deciding what to prove.
